## 一、这篇文章当前的核心写法

当前论文不是按“我们已经做成了一个稳定提升的 skill 进化系统”去写。  
它的更准确定位是：

> **一篇框架型（framework-oriented）的研究论文，带有初步实证结果。**

也就是说，这篇文章的目标不是证明“skill 已经稳定演化成功”，而是要论证三件事：

1. 这个研究问题在漏洞分析场景里是成立且重要的；
2. 我们已经把它做成了一个可运行、可观察、可测量的闭环；
3. 初步实验已经表明，真正难的问题在哪里。

目前论文把“真正难的问题”明确定位为：

- 不是 skill 能不能生成；
- 也不是 blind run 能不能执行；
- 而是 **candidate skill 是否应该进入 live skill 库**。

## 二、章节设计逻辑

---

## 第 1 章：Introduction

### 这一章要做什么

引言承担四个任务：

1. 把 skill、agent、漏洞分析三条研究线接起来；
2. 说明“更多 skill 并不天然更好”；
3. 提出本文真正研究的问题；
4. 给出贡献点。

### 当前写法的核心逻辑

引言不是从“我们做了个系统”开始，而是从“已有 skill 研究已经很多，但 run-to-library transition 还没被写清楚”开始。  
这会让整篇文章更像研究论文，而不是工程报告。

### 当前最重要的一句话

当前引言最关键的立题句，其实是：

> 在真实漏洞分析工作流中，最难的问题不是生成一个 candidate skill，而是判断一次完成的运行是否包含了值得写入 live skill 库的可复用程序性知识。

### 现阶段支撑程度

这个立题是**成立的**，因为工程和实验已经说明：

- blind 运行是可以做的；
- candidate 是可以生成的；
- 但是进入 live skill 库很难。

### 后续还能怎么加强

后续如果实验进一步成功，可以在引言中更明确补一句：

> 在某些 case 上，是否注入某个 skill 会显著改变漏洞是否能被正确定位。

这会把“问题重要性”再提高一层。

---

## 第 2 章：Problem Formulation

### 这一章要做什么

问题形式化的目的不是炫公式，而是把全文讨论从口语化问题转成三个更清晰的研究对象：

1. 什么是一次运行；
2. 什么是 skill 的作用；
3. 什么是 candidate skill 的发布问题。

### 当前章节里的三个核心概念

#### 1. 运行对象

\[
r=(x,S_r,\tau,y,E)
\]

强调一次运行不是只有答案，还包括：

- 输入任务；
- 被注入的 skill；
- 轨迹；
- 最终输出；
- 外部证据。

#### 2. skill 归因问题

\[
\Delta(s)=q_{\mathrm{task}}(y_s)-q_{\mathrm{task}}(y_0)
\]

这一公式的作用不是让文章变得“数学化”，而是明确告诉读者：

> 我们真正想知道的是：有 skill 和没 skill 的结果差异。

而当前工程里还没有低成本、严格、普适地解决这个问题。

#### 3. 发布问题

\[
\mathrm{Publish}(\Delta s)=
\mathbb{I}[
\mathrm{EvidenceSufficient}(\Delta s)\land
\mathrm{FollowupPass}(\Delta s)]
\]

这一定义把 gate 从工程细节上升成了论文里的独立问题对象。

### 现阶段支撑程度

这一章的形式化和工程现状是匹配的。  
尤其是“归因尚未严格解决，但发布问题已经非常真实”这一点，和现有实验完全一致。

### 后续还能怎么加强

如果后续真的做了：

- counterfactual gate；
- retention gate；
- 多轮 candidate/live 对比；

那么这一章可以再加入更完整的 publish / retain 两阶段定义。

---

## 第 3 章：Evidence-Constrained Skill Evolution Framework

### 这一章要做什么

这一章是全文的方法主轴。  
它回答的问题不是“我们系统有哪些模块”，而是：

> 在漏洞分析场景里，证据如何约束 skill 演化闭环？

### 当前的几个子模块为什么这样排

#### 3.1 Blind Execution

先讲 blind 执行，是因为全文的实验可信性首先依赖“分析阶段不能提前知道答案”。

#### 3.2 Auditable Skill Injection

再讲 skill 注入审计，是为了说明：

- 我们至少知道这轮到底注入了什么；
- 也知道这些注入内容对应哪一段会话。

这一步不是因果归因，但它是归因研究的前提。

#### 3.3 Multi-Evidence Confirmation

这一步定义了本文为什么不是普通 agent benchmark：  
漏洞分析允许引入独立于模型叙述之外的外部证据。

#### 3.4 Evidence-Conditioned Feedback

这里的四级标签不是作为“创新理论”来写，而是作为：

> 一个可供演化系统消费的、低成本运行后接口。

这点现在的写法比以前更稳。

#### 3.5 Candidate-Level Publication Gate

这一节是当前整篇文章最关键的方法点之一，因为它把 candidate 和 live skill 分开了。

#### 3.6 Live / Candidate / Share Separation

这部分看起来像工程组织，但实际上对实验设计很重要。  
如果不分离，candidate 会污染下一轮运行，实验就不干净了。

### 现阶段支撑程度

这一章和工程是高度一致的。  
它也是最能经得住质疑的一章之一，因为很多内容都能在代码路径和运行数据里落地。

### 后续还能怎么加强

如果后面真正做了：

- catalog + inline 的更合理混合；
- 远端运行环境模块化接入；
- retention / demotion 机制；

这一章就可以再扩展成更完整的 lifecycle 设计。

---

## 第 4 章：Prototype Realization

### 这一章要做什么

这一章是“把前面的框架落到当前原型里”。  
它的作用是告诉审稿人：

- 这不是纯概念；
- 也不是完全虚构的 pipeline；
- 当前工程已经可以支撑研究问题。

### 当前应该如何理解这一章

它不是在炫工程复杂度，而是在说明：

1. analysis plane 和 confirmation plane 如何分离；
2. benchmark case 如何定义；
3. score / validator / handoff / evolve 是如何串起来的；
4. 为什么这些实现足够支撑论文里的主张。

### 当前最需要注意的边界

这一章不能写得太像产品说明书。  
所以目前稿子已经有意避免展开太多脚本级细节，而是强调：

- 研究需要的关键机制是什么；
- 这些机制在原型里如何存在。

---

## 第 5 章：Experimental Methodology

### 这一章要做什么

实验方法章负责回答：

1. 我们测什么；
2. 怎么测；
3. 哪些变量固定，哪些变量变化；
4. 当前结论能推到什么程度，不能推到什么程度。

### 当前实验设计分成两层

#### 第一层：6 个 case 的 36 次主 A/B

这是主结果层，用于回答：

- skill 是否有异质性；
- 是否存在明显有害 case；
- 是否存在明显无效 case。

#### 第二层：2 个 CGI case 的 16 次 profile 消融

这是机制解释层，用于回答：

- topic relevant 是否足够；
- seed / live / wrong / none 之间差在哪里；
- 为什么某些 skill 看起来相关却并没有真正帮助。

### 为什么这样分层是合理的

如果把所有实验混成一锅，文章会显得杂。  
现在这样分层之后：

- 主 A/B 负责“总体结论”；
- CGI 消融负责“机制洞察”。

这是比较像论文的组织方式。

---

## 第 6 章：Results

### 这一章要做什么

结果章当前承担三个层次的论证：

1. 证明 skill 效果确实不稳定；
2. 说明轻量级反馈在方向上是有用的；
3. 证明 gate 才是当前闭环真正的瓶颈。

### 6.1 为什么先讲 A/B 结果

因为要先回答一个最基础的问题：

> skill 到底有没有影响结果？

如果这一步都没成立，后面的演化和 gate 讨论都站不住。

### 6.2 为什么加入 CGI profile ablation

因为仅靠 A/B 还无法区分：

- skill 没帮助，是因为 topic 不对；
- 还是 topic 对，但程序结构不对。

这一节正是为了解决这个问题。

### 6.3 为什么还要讲反馈信号

因为论文不是只关心“分数”，还关心：

> 当前闭环里，演化系统拿到的是什么信号。

这一步把实验结果和 evolution feedback 连接起来。

### 6.4 为什么 gate 单独成节

因为目前最像论文发现的，不是“某个 skill 均值更高”，而是：

> candidate 生成并不是最难的，发布才是最难的。

这一点值得单独成节。

---

## 第 7 章：Discussion

### 这一章要做什么

讨论章负责把实验结果提升成更一般的研究认识。

### 当前讨论章的几个关键点

#### 1. 证据–归因鸿沟

这是全文目前最重要的概念性总结之一：

- 外部证据能验证“找到了什么”；
- 但不能直接验证“为什么找得到”。

#### 2. skill library design implication

这一步把实验发现提升为系统设计启示：

- skill 选择应该更 case-sensitive；
- 评估也应该更 case-sensitive。

#### 3. Toward a counterfactual gate

这一步给后续工程和实验留下非常明确的方向：

- Scheme A：严格对比 with-skill / no-skill；
- Scheme B：先允许 non-inferior，再做 retention。

这一节其实也是后续工程工作的理论目标。

---

## 第 8 章：Related Work

### 这一章要做什么

相关工作章现在最重要的任务不是“把论文列全”，而是防止我们误报创新。

### 当前相关工作分成的几组是合理的

1. skill 生成 / 复用 / 演化  
2. verifier / environment 驱动的 skill 修正  
3. skill 失败 / misevolution / 治理  
4. 安全代理 / playbook / benchmark

这样的好处是：

- 不会把自己写成“首次做 skill 演化”；
- 也不会把自己写成“首次做安全 agent”；
- 而是把文章定位在：  
  **安全场景中 run-to-library transition 的治理问题。**

---

## 第 9 章：Threats to Validity

### 这一章要做什么

这一章是为了提前把最容易被质疑的点自己说出来。

当前列出的局限整体是合理的，特别是：

1. 样本量还小；
2. 模型波动明显；
3. 四级反馈不是严格因果估计器；
4. gate 历史数据跨多个开发阶段；
5. blind case 仍有泄漏风险。

这会让论文显得更诚实，也更像研究论文。

---

## 第 10 章：Conclusion

### 这一章要做什么

结论章当前最重要的是避免说过头。

现在最合适的落点是：

1. 我们已经把闭环做成可研究对象；
2. 初步实验说明 skill 作用确实异质；
3. 真正瓶颈在发布控制；
4. 下一步关键不是“再多写 candidate”，而是“更可靠地决定哪些 candidate 值得进入 live skill 库”。

### 当前这个结论为什么是稳的

因为它和当前工程及实验状态完全一致：

- 没有夸大为“已经实现稳定 skill 进化”；
- 但也没有退回成“只是做了个原型系统”。

---

## 三、当前论文最适合对外讨论的定位

如果现在用于学术讨论，我建议你把这篇稿子定位成：

> **围绕漏洞分析代理的 skill 演化闭环问题，提出一套证据约束型生命周期框架，并给出初步实验和系统实证。**

不要把它讲成：

- 一个已经稳定有效的 skill 进化系统；
- 一个已经解决严格因果归因的工作；
- 一个只是在讲 benchmark / harness 的工程实现。

---

## 四、后续最值得优先补强的部分

从论文角度看，后续最值得增强的优先级是：

### 优先级 1：补强“candidate 进入 live skill 后是否真的改善后续运行”

这是整篇文章目前最缺、同时最有分量的证据。

### 优先级 2：补强“skill 必要性”证据

也就是更强地证明：

- 没有某个 skill 找不到；
- 有了它才找到。

### 优先级 3：补强 gate 的对照实验

例如：

- replay-only
- non-inferiority
- counterfactual ablation

这会让第 7 章讨论更扎实。

### 优先级 4：扩展 case 类型

当前 case 还是偏集中。  
如果后续能把固件之外的漏洞案例也更系统地放进来，论文普适性会更强。

---

## 五、当前这篇论文最强和最弱的地方

### 当前最强的地方

1. 问题意识比较清楚；
2. 工程闭环与论文问题能对上；
3. “发布控制是瓶颈”这个结论比较像真正的研究发现；
4. 远端 blind + 本地确认 的 split-plane 写法比较有辨识度。

### 当前最弱的地方

1. 还没证明 stable improvement；
2. 还没证明 strict necessity；
3. gate 的结论很强，但正例还少；
4. 样本量仍偏小。

---

## 六、一句话总结

如果要用一句话总结当前文章，可以说：

> 这篇文章当前最有价值的地方，不是证明 skill 已经能稳定自我进化，而是把“漏洞分析中的 skill 为什么难以安全、可信地进入 live 库”这个问题首次做成了一个可运行、可测量、可讨论的研究对象。
